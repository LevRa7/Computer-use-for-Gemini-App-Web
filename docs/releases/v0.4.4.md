## 🔧 Antigravity Mesh v0.4.4

A confirmation prompt is now spent on a **system change** and nothing else. The
device branch — camera, microphone, location, SMS, contacts — stops asking, and
so does `unshare`; what still refuses those calls is the node's own switch, not a
dialog. No tool name, argument or capability changed.

### 🔓 Only a system change interrupts you now

Gemini Spark decides whether to stop with *"confirm this action?"* from the MCP
annotation hints in `tools/list`. One profile was carrying `destructiveHint: true`
without ever deleting anything: the sensitive class, which held `device_capture`
and `device_messages`. It is gone.

| Class | Tools | Confirmation |
| :--- | :--- | :--- |
| Read-only | `mesh_status`, `system_info`, `system_vitals`, `get_orchestration_skill`, `list_dir`, `read_file`, `grep_search`, `glob_find`, `job_output`, `job_list`, `share_list`, `device_info` | never asked |
| Local work — commands, builds, file writes, jobs, shares, and the whole device branch | `bash_exec`, `run_job`, `write_file`, `edit_file`, `job_kill`, `share_file`, `serve_dir`, `unshare`, `device_control`, `device_capture`, `device_messages` | not asked |
| **Confirmed — install/delete, `sudo`, system paths** | `system_change`, `system_write`, `mesh_update` | **asked first** |

- `device_capture` and `device_messages` leave the sensitive class. They install
  and remove nothing, so a dialog on a camera or an SMS list buys no safety — it
  only trains the operator to click through the prompts that matter.
- The gateway, whose `tools/list` the client actually reads, now advertises the
  whole device branch and `unshare` as read-only, because Gemini Spark skips its
  dialog only for a hint it sees as `readOnlyHint: true` — the same mechanism the
  gateway already used for `bash_exec`, `write_file` and the share tools. The
  node's own list keeps the literal hint and a test pins the difference.
- `unshare` follows them out of the destructive class. Revoking a public link
  stops a local server and removes a copy the operator can publish again in one
  call; it is not an install, a delete or a system path.
- What actually refuses a device call did not move and is not a hint: the node's
  `MESH_DEVICE`, `MESH_DEVICE_ACTIONS`, `MESH_DEVICE_PIM` and `MESH_READ_ONLY`
  reject the call before any `termux-*` command runs, whatever the client does
  with the hints.
- `mesh_update` stays destructive on the node, and the gateway keeps
  `system_change` / `system_write` destructive: those three install, delete or
  replace something that cannot be undone in one call. They are the only remaining
  prompts.
- Both surfaces were changed together: `core/mcp_tools.py` (`TOOL_ANNOTATIONS`)
  and `gateway.py` (its own static table), which
  `tests/test_gateway_share_route.py` compares hint for hint. The device tool
  descriptions in both files stay word for word identical.
- Pinned by `tests/test_tool_annotations.py` in both directions — destructive is
  exactly `{mesh_update}`, no device tool may carry `destructiveHint`, and
  `unshare` may not drift back — plus
  `tests/test_gateway_command_policy.py` on the gateway's surface.

> [!IMPORTANT]
> The gateway's `tools/list` is static and deployed separately: an installed node
> picks the new annotations up with the node update, but the client keeps seeing
> the old hints until the gateway is re-deployed (`deploy_gateway.sh`). Deploy it
> before expecting a silent camera call.

### 📚 Documents follow the policy

README (both halves), `docs/TERMUX.md` (both halves), `CORE.md`,
`skills/orchestrator.md` and the standalone server's `instructions`
(`core/server.py`) now say what the code does: no dialog on the device branch,
and the node-side switches are the guarantee. The gateway's `instructions` string
was updated the same way.
