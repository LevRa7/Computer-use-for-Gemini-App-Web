## 🔧 Antigravity Mesh v0.4.1

A patch release with two fixes that only a **real phone** could have found. Both
were visible in the very first device report from an OPPO PHY110 on Android 16:
`cpu: 0` and `memory: 0.0/0.0 MB used`. Nothing else changed.

### 🧠 The CPU model is no longer a core index

An Android `/proc/cpuinfo` contains per-core `processor : N` lines and **no**
`Hardware` and **no** `model name` line, so a parser that looks for those (and
accepts `Processor` case-insensitively) answered with the literal `"0"` — a core
number reported as the chip.

- A value made of digits only is now skipped, and when `cpuinfo` names nothing the
  SoC comes from Android's own properties: **`ro.soc.model`** (Android 12+), then
  `ro.board.platform`, `ro.hardware`, `ro.product.board`.
- On the reference phone the report now says `cpu: SM8650, 8 cores` instead of
  `cpu: 0`.

### 🧮 A phone reports its RAM again

Python 3.13+ answers `platform.system() == "Android"` on a phone, and
`core/vitals.py` knew only `Linux`, `Darwin` and `Windows` — so neither branch ran
and the collector returned 0 MB of RAM while the same report showed a real 84 %
battery reading.

- The presence of `/proc/meminfo` now decides the Linux path, which is what a phone
  takes: Android is Linux underneath.
- `core/device.py` no longer trusts a zero total blindly. It re-reads
  `/proc/meminfo` through the module's own reader — so a *simulated* phone in the
  tests takes the same path as a real one — and if neither source answers it says
  so instead of reporting zeros.
- The same report now says `memory: 10367.7/15204.0 MB used (68.2 %)`.

### 📱 Verified on the device, not only in the tests

The branch was run against a real phone through the gateway, and every block
answered with real hardware values: battery **83 % discharging**, Wi-Fi
**Warmen −65 dBm** at 5225 MHz, cellular **Cellfie / lte −98 dBm (level 2)**,
**4 cameras** (the first: back, 4096×3072), **12 sensors** listed without sampling
them, and `capabilities` reporting `app_reachable: true` with the Termux:API app
installed.

The same session also exposed why a phone node keeps disappearing: the report said
`wake_lock: held: false` — nothing was holding Android's wake lock, so the system
freezes (and eventually kills) Termux when the screen goes off. That is a
deployment matter rather than a code defect: install `termux-services` and
Termux:Boot, keep battery optimisation off, and let the installer's boot script
take the wake lock — [`docs/TERMUX.md`](../TERMUX.md) covers all of it.

### 🧪 Tests

`1172 passed, 3 skipped` (the new Android vitals test is POSIX-only), including
three regressions that pin the facts above: a `cpuinfo` with only `processor : N`
lines, an Android build that answers `ro.board.platform` instead of `ro.soc.model`,
and `platform.system() == "Android"` still producing a real RAM reading.

Updating is the usual one call: `mesh_update` with `action=apply`, or the CLI
`gemini-computer-use update`.
