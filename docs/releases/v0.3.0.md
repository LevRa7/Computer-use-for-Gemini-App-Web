## 🚀 Antigravity Mesh v0.3.0

Nodes now keep themselves current. A node checks GitHub for a newer release,
verifies the download against a published SHA-256, installs it with a rollback
backup and restarts itself — so a machine nobody logs into is no longer a machine
stuck on the version it was set up with.

### 🔄 Self-update

- **`core/updater.py`** is the whole mechanism, standard library only: it asks the
  GitHub Releases API, compares the tag with `core/version.py`, downloads
  `mesh-payload-<version>.zip`, checks its SHA-256, swaps `core/`, `skills/` and
  `ops/` and brings the agent back. It runs on a Windows box with nothing but
  python.org's Python, on a VPS and on macOS.
- **The agent checks in the background** (every six hours by default) and records
  the answer in `agent.heartbeat`, so `ops/doctor.ps1` can say "a newer release
  exists" — or "the last check failed" — without touching the network.
- **Nothing unverified is ever installed.** A payload without a published checksum
  is refused (`MESH_UPDATE_ALLOW_UNVERIFIED=1` overrides it deliberately), and a
  mismatch deletes the download and backs off for an hour instead of retrying in a
  loop.
- **Every swap is reversible.** The replaced directories are moved to
  `~/.config/antigravity-mesh/backups/<old-version>-<timestamp>/`, and a journal
  written *before* the swap lets the next start undo an update that was
  interrupted by a kill or a power cut. The worst case is "still on the old
  version", never "half of two versions".
- **The node really does come back new.** A detached helper waits for the old
  agent to exit and restarts it through its supervisor (the Windows watchdog task,
  `systemctl --user restart agy-agent.service`, `launchctl kickstart -k`, or a
  plain detached `python -m core.agent`). An update applied from the CLI or the
  scheduled task while an agent kept running stops that agent first: otherwise the
  new one would wait forever for the instance lock the old one never releases.

### 🧰 Four ways to drive it

| | |
| :--- | :--- |
| Gemini | `mesh_update` — `action=status`, `check` or `apply` |
| CLI | `gemini-computer-use update [-Check] [-Force] [-NoRestart] [-Json]` |
| Python | `python -m core.updater --status \| --check \| --apply [--json]` |
| Windows | `ops/update.ps1` — what the new daily task runs |

`ops/update.ps1` exists because two things are Windows-only: which interpreter the
node is pinned to and where the payload lives. It reads both from the Startup
launcher the installer wrote and refuses the Microsoft Store alias, the
interpreter that once left a node offline for a day. `install.ps1` now registers
the `AntigravityMeshUpdater` task (daily at 03:30) next to the existing watchdog.

### 📦 Releases that nodes can consume

`.github/workflows/release.yml` turns a pushed tag into everything an update needs:
it checks that the tag, `core/version.py` and `package.json` agree, runs the
updater and version tests, builds and self-tests the Windows setup, builds the
updatable payload archive, and attaches all four assets to the release. Notes come
from `docs/releases/<tag>.md`.

`mesh-payload-<version>.zip` is built by the new `tools/build-payload-zip.py`
rather than by `Compress-Archive`: PowerShell writes backslashes into entry names,
and Python's `zipfile` treats a backslash as an ordinary character on POSIX, so
such an archive would unpack into files literally named `core\agent.py`. The tool
also drops `__pycache__` — a payload carrying bytecode whose timestamps match the
sources it came from would make the node run the old code under the new names — and
fixes timestamps, so the same tree always hashes the same.

### 📌 One version, declared once

The version now lives in `core/version.py` alone. `package.json` must name the same
number (the build fails otherwise), the release workflow verifies the tag against
it, and `tests/test_version_single_source.py` pins all of it. A version that lives
in two files is a version that eventually disagrees with itself — and an updater
comparing the wrong number either reinstalls forever or never updates at all.

### ✅ Tests

`399 passed` on Windows; `tests/test_updater.py` alone runs 99 checks with no
network at all — real archives over `file://` URLs, so the download, the SHA-256
verification and the extraction all execute for real, plus backup, rollback,
recovery from an interrupted swap, the CLI, the MCP tool and the restart logic.
The new CI workflow runs the suite on Linux (3.11 and 3.13) and Windows, and builds
the payload and the setup on every change.
