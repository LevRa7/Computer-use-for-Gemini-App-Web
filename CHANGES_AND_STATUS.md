### Б. Ядро инструментов: `core/mcp_tools.py` (Локальные изменения, готовые к коммиту)
- **Что сделано:**
  1. **Исправлен фатальный сбой Windows при импорте:** В стандартной библиотеке Python под Windows модуль `signal` не имеет атрибутов `SIGKILL`, `SIGHUP`, `SIGQUIT`. Ранее в словаре `_SIGNALS` было прямое обращение к ним, из-за чего агент на Windows падал с `AttributeError` при старте. Теперь сигналы собираются динамически через `getattr(..., hasattr)`.
  2. **Кроссплатформенное завершение процессов (`job_kill`):** 
     - На POSIX (Linux/macOS) по-прежнему используется отправка сигналов группе процессов (`os.killpg`).
     - Для Windows добавлена функция `_kill_tree_windows`, которая использует нативную системную команду `taskkill /T /F /PID <pid>` для гарантированного уничтожения всего дерева дочерних процессов.
  3. **Безопасная проверка живучести PID на Windows (`_pid_alive_windows`):**
     - На POSIX вызов `os.kill(pid, 0)` проверяет наличие процесса.
     - На Windows `os.kill` не поддерживает нулевой сигнал (любой сигнал, кроме `CTRL_C`/`CTRL_BREAK`, приводит к вызову `TerminateProcess`, то есть проверка просто убивала сам процесс).
     - Теперь на Windows проверка выполняется через вызовы Win32 API (`kernel32.OpenProcess` + `GetExitCodeProcess` со статусом `STILL_ACTIVE`).
  4. **Автоопределение оболочки команд (`command_shell`):**
     - В Windows вызов `bash` из PATH часто запускает заглушку WSL из `System32`, которая либо падает, либо выполняет команды внутри контейнера WSL вместо хостовой ОС Windows.
     - Теперь приоритетно ищется настоящий Git Bash (`Git\bin\bash.exe`). Если он не найден — команды прозрачно исполняются через PowerShell (`pwsh` или `powershell.exe -ExecutionPolicy Bypass`).
     - Подавлены всплывающие окна консолей Windows при вызове команд (`CREATE_NO_WINDOW`).
  5. **Отображение активного шелла:** В `system_info` добавлено поле `command_shell`, чтобы модель сразу знала, какой синтаксис (Bash или PowerShell) ожидает хост.

### В. Агент и туннель: `core/agent.py` (Локальные изменения, готовые к коммиту)
- **Что сделано:**
  1. **Параллельная обработка вызовов инструментов (`asyncio.create_task`):**
     - Ранее входящие вызовы `tools/call` обрабатывались строго последовательно в цикле получения сообщений из вебсокета. Если один инструмент выполнялся 15-20 секунд (например, долгий curl или сборка), следующий вызов стоял в очереди и выбивал таймаут шлюза (28 с) или таймаут самого Gemini.
     - Теперь каждый запрос запускается в независимой корутине `_serve_call`, не блокируя вебсокет и пинги поддержания связи.
  2. **Защита от взаимного выбивания туннелей (`InstanceLock`):**
     - На шлюзе действует правило: новое подключение с тем же именем узла вытесняет предыдущее. Если пользователь случайно запускал два агента одновременно (или служба перезапускалась при висящем процессе), они входили в бесконечный шквал взаимных переподключений («флаппинг»), ломая все текущие запросы.
     - Добавлена кроссплатформенная файловая блокировка процесса (`fcntl` на Linux/macOS, `msvcrt` на Windows). Второй агент терпеливо ждёт освобождения блокировки.
  3. **Бесшовное чтение переменных окружения из конфига:**
     - Агент теперь умеет читать параметры из `~/.config/antigravity-mesh/agent.env`, даже если они не проброшены в глобальный `os.environ` (актуально для автозапуска Windows через VBS/реестр). Учтена поддержка BOM UTF-8 (PowerShell 5).
  4. **Интеллектуальная обработка разрывов и 401/403 Unauthorized:**
     - Различает временные разрывы сети (быстрый exponential backoff с джиттером от 1 до 15 сек) и ошибки авторизации `4001 Unauthorized` / `HTTP 403` (таймаут 60 сек, чтобы не перегружать шлюз запросами при неверном токене).
     - Обрабатывает как чистые разрывы, так и тихие зависания сокета (`open_timeout=15`, `ping_interval=10`, `ping_timeout=10`).

### Г. Политика подтверждений MCP: спрашивать только про установку и удаление (Локальные изменения, готовые к коммиту)
- **Проблема:** Gemini Spark запрашивал подтверждение буквально на каждое действие этого MCP, тогда как другие MCP-серверы работали без диалога. Причина — в `tools/list` не публиковались **MCP-аннотации** (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). По умолчанию спецификации инструмент без аннотаций считается деструктивным (`readOnlyHint=false`, `destructiveHint=true`), и клиент переспрашивает перед каждым вызовом.
- **Что сделано:**
  1. В `core/mcp_tools.py` добавлены четыре профиля аннотаций и таблица `TOOL_ANNOTATIONS` — одна строка на инструмент; профиль подставляется в спеку при импорте, поэтому `tools/list` узла (и standalone-сервер `core/server.py`, который берёт те же `TOOLS`) отдаёт подсказки автоматически.
  2. Классы: *read-only* (чтение и осмотр — без вопросов), *local write* (`bash_exec`, `run_job`, `write_file`, `edit_file`, `job_kill` — без вопросов), *publish* (`share_file`, `serve_dir` — `openWorldHint=true`, но не деструктивно), *destructive* (`mesh_update`, `unshare` — подтверждение запрашивается).
  3. `gateway.py` не может импортировать код узла и держит собственный статический `tools/list`, поэтому такая же таблица и функция `annotate_tools()` добавлены туда; тест `test_advertised_confirmation_hints_match_the_node` сравнивает подсказки шлюза и узла по каждому инструменту.
  4. Новый `tests/test_tool_annotations.py` фиксирует политику: у каждого инструмента есть все четыре подсказки, набор read-only инструментов совпадает с объявленным, деструктивными помечены ровно `mesh_update` и `unshare`.
- **Почему `job_kill` не в списке подтверждаемых:** остановка фоновой задачи — это не установка и не удаление, а `bash_exec` (который по требованию работает без диалога) всё равно может завершить тот же процесс; отдельный гейт на `job_kill` не защищал бы ничего, только возвращал бы лишний запрос. Перенести его обратно — одна строка в `TOOL_ANNOTATIONS` (обе стороны: `core/mcp_tools.py` и `gateway.py`).
- **Ограничение, зафиксированное в README:** `bash_exec`/`run_job` универсальны, и `apt install` или `rm` внутри них аннотацией не пометить — подсказки статичны на инструмент. Жёсткая гарантия остаётся за переключателями узла `MESH_READ_ONLY` и `MESH_WRITE_ROOTS`.
- **Важно для выката:** узел получает изменение вместе с обновлением кода, а **шлюз — только после повторного деплоя** (`deploy_gateway.sh`), иначе Gemini Spark продолжит видеть старый `tools/list` без аннотаций.
- **Проверка:** `python -m pytest -q` — 409 passed, 1 skipped.

## 2. Анализ вопроса: «Есть ли смысл использовать так много инструментов для MCP из агентской среды?»

### Вердикт:
**Да, текущее разделение на 19 инструментов полностью оправдано и необходимо.** Вот почему агент не может обойтись одним лишь универсальным `bash_exec`:

1. **Ограничение контекста и лимиты Gemini:**
   - Если агент будет делать `bash_exec("cat big_file.txt")`, весь файл разом вывалится в контекст, забьёт токенный лимит модели или обрежется.
   - Специализированный `read_file(path, start_line, end_line)` позволяет агенту читать файлы постранично и точно исследовать код.
2. **Безопасность редактирования:**
   - Редактировать файлы через bash (sed, awk, echo) из LLM чревато синтаксическими ошибками, проблемами с экранированием кавычек и спецсимволов.
   - `edit_file(path, old_string, new_string)` и `write_file` гарантируют атомарность и точечную правку без потери содержимого.
3. **Проблема жесткого таймаута Gemini (25-30 секунд):**
   - У клиентов Gemini (особенно в Web/App Spark) есть строгий тайм-лимит на один ответ инструмента (около 30 с).
   - Команды вроде `npm install`, `docker build`, `git clone` или бэкапы гарантированно упадут по таймауту в обычном bash.
   - Связка `run_job` + `job_output` / `job_list` / `job_kill` — единственный способ для мобильного агента запускать тяжёлые фоновые процессы и возвращаться за результатом.
4. **Кроссплатформенность (Windows):**
   - На Windows без Bash вызовы `grep`, `find`, `ls -la`, `ps aux` не работают или требуют громоздких конструкций PowerShell.
   - Инструменты `grep_search`, `glob_find`, `list_dir`, `system_vitals` работают на чистом Python одинаково на любой ОС.

## 3. Проверка надежности работы в фоне и восстановления связи

| Компонент / Платформа | Linux | macOS | Windows | Статус надежности |
| :--- | :---: | :---: | :---: | :--- |
| **Установка в 1 строку** | `install.sh` | `install.sh` | `install.ps1` | **Отлично**. Автоопределение типа устройства, Python, venv, генерация токенов. |
| **Фоновая служба** | `systemd --user` + linger | `launchd` (LaunchAgents plist) | `Startup\antigravity-agent.vbs` | **Отлично**. Переживает перезагрузки системы. |
| **Реконнект при обрыве сети** | Авто (1–15 с) | Авто (1–15 с) | Авто (1–15 с) | **Проверено**. Пинги каждые 10 с, автоматический реконнект с экспоненциальным backoff. |
| **Защита от гонки процессов** | `fcntl.flock` | `fcntl.flock` | `msvcrt.locking` | **Проверено**. Не дает двум процессам бесконечно выбивать друг друга со шлюза. |
| **Обработка команд** | Bash | Bash / zsh | Git Bash / PowerShell | **Исправлено**. Устранены Windows-падения `signal` и вызовы `os.kill(0)`. |
