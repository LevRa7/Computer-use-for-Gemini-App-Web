### Б. Ядро инструментов: `core/mcp_tools.py` (Локальные изменения, готовые к коммиту)
- **Что сделано:**
  1. **Исправлен фатальный сбой Windows при импорте:** В стандартной библиотеке Python под Windows модуль `signal` не имеет атрибутов `SIGKILL`, `SIGHUP`, `SIGQUIT`. Ранее в словаре `_SIGNALS` было прямое обращение к ним, из-за чего агент на Windows падал с `AttributeError` при старте. Теперь сигналы собираются динамически через `getattr(..., hasattr)`.
  2. **Кроссплатформенное завершение процессов (`job_kill`):** 
     - На POSIX (Linux/macOS) по-прежнему используется отправка сигналов группе процессов (`os.killpg`).
     - Для Windows добавлена функция `_kill_tree_windows`, которая использует нативную системную команду `taskkill /T /F /PID <pid>` для гарантированного уничтожения всего дерева дочерних процессов.
  3. **Безопасная проверка живучести PID на Windows (`_pid_alive_windows`):**
     - На POSIX вызов `os.kill(pid, 0)` проверяет наличие процесса.
     - На Windows `os.kill` не поддерживает нулевой сигнал (любой сигнал, кроме `CTRL_C`/`CTRL_BREAK`, приводит к вызову `TerminateProcess`, то есть проверка просто убивала сам процесс).
     - Теперь на Windows проверка выполняется через вызовы Win32 API (`kernel32.OpenProcess` + `GetExitCodeProcess` со статусом `STILL_ACTIVE`).
  4. **Автоопределение оболочки команд (`command_shell`):**
     - В Windows вызов `bash` из PATH часто запускает заглушку WSL из `System32`, которая либо падает, либо выполняет команды внутри контейнера WSL вместо хостовой ОС Windows.
     - Теперь приоритетно ищется настоящий Git Bash (`Git\bin\bash.exe`). Если он не найден — команды прозрачно исполняются через PowerShell (`pwsh` или `powershell.exe -ExecutionPolicy Bypass`).
     - Подавлены всплывающие окна консолей Windows при вызове команд (`CREATE_NO_WINDOW`).
  5. **Отображение активного шелла:** В `system_info` добавлено поле `command_shell`, чтобы модель сразу знала, какой синтаксис (Bash или PowerShell) ожидает хост.

### В. Агент и туннель: `core/agent.py` (Локальные изменения, готовые к коммиту)
- **Что сделано:**
  1. **Параллельная обработка вызовов инструментов (`asyncio.create_task`):**
     - Ранее входящие вызовы `tools/call` обрабатывались строго последовательно в цикле получения сообщений из вебсокета. Если один инструмент выполнялся 15-20 секунд (например, долгий curl или сборка), следующий вызов стоял в очереди и выбивал таймаут шлюза (28 с) или таймаут самого Gemini.
     - Теперь каждый запрос запускается в независимой корутине `_serve_call`, не блокируя вебсокет и пинги поддержания связи.
  2. **Защита от взаимного выбивания туннелей (`InstanceLock`):**
     - На шлюзе действует правило: новое подключение с тем же именем узла вытесняет предыдущее. Если пользователь случайно запускал два агента одновременно (или служба перезапускалась при висящем процессе), они входили в бесконечный шквал взаимных переподключений («флаппинг»), ломая все текущие запросы.
     - Добавлена кроссплатформенная файловая блокировка процесса (`fcntl` на Linux/macOS, `msvcrt` на Windows). Второй агент терпеливо ждёт освобождения блокировки.
  3. **Бесшовное чтение переменных окружения из конфига:**
     - Агент теперь умеет читать параметры из `~/.config/antigravity-mesh/agent.env`, даже если они не проброшены в глобальный `os.environ` (актуально для автозапуска Windows через VBS/реестр). Учтена поддержка BOM UTF-8 (PowerShell 5).
  4. **Интеллектуальная обработка разрывов и 401/403 Unauthorized:**
     - Различает временные разрывы сети (быстрый exponential backoff с джиттером от 1 до 15 сек) и ошибки авторизации `4001 Unauthorized` / `HTTP 403` (таймаут 60 сек, чтобы не перегружать шлюз запросами при неверном токене).
     - Обрабатывает как чистые разрывы, так и тихие зависания сокета (`open_timeout=15`, `ping_interval=10`, `ping_timeout=10`).

### Г. Политика подтверждений MCP: спрашивать только про установку и удаление (Локальные изменения, готовые к коммиту)
- **Проблема:** Gemini Spark запрашивал подтверждение буквально на каждое действие этого MCP, тогда как другие MCP-серверы работали без диалога. Причина — в `tools/list` не публиковались **MCP-аннотации** (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). По умолчанию спецификации инструмент без аннотаций считается деструктивным (`readOnlyHint=false`, `destructiveHint=true`), и клиент переспрашивает перед каждым вызовом.
- **Что сделано:**
  1. В `core/mcp_tools.py` добавлены четыре профиля аннотаций и таблица `TOOL_ANNOTATIONS` — одна строка на инструмент; профиль подставляется в спеку при импорте, поэтому `tools/list` узла (и standalone-сервер `core/server.py`, который берёт те же `TOOLS`) отдаёт подсказки автоматически.
  2. Классы: *read-only* (чтение и осмотр — без вопросов), *local write* (`bash_exec`, `run_job`, `write_file`, `edit_file`, `job_kill` — без вопросов), *publish* (`share_file`, `serve_dir` — `openWorldHint=true`, но не деструктивно), *destructive* (`mesh_update`, `unshare` — подтверждение запрашивается).
  3. `gateway.py` не может импортировать код узла и держит собственный статический `tools/list`, поэтому такая же таблица и функция `annotate_tools()` добавлены туда; тест `test_advertised_confirmation_hints_match_the_node` сравнивает подсказки шлюза и узла по каждому инструменту.
  4. Новый `tests/test_tool_annotations.py` фиксирует политику: у каждого инструмента есть все четыре подсказки, набор read-only инструментов совпадает с объявленным, деструктивными помечены ровно `mesh_update` и `unshare`.
- **Почему `job_kill` не в списке подтверждаемых:** остановка фоновой задачи — это не установка и не удаление, а `bash_exec` (который по требованию работает без диалога) всё равно может завершить тот же процесс; отдельный гейт на `job_kill` не защищал бы ничего, только возвращал бы лишний запрос. Перенести его обратно — одна строка в `TOOL_ANNOTATIONS` (обе стороны: `core/mcp_tools.py` и `gateway.py`).
- **Ограничение, зафиксированное в README:** `bash_exec`/`run_job` универсальны, и `apt install` или `rm` внутри них аннотацией не пометить — подсказки статичны на инструмент. Жёсткая гарантия остаётся за переключателями узла `MESH_READ_ONLY` и `MESH_WRITE_ROOTS`.
- **Важно для выката:** узел получает изменение вместе с обновлением кода, а **шлюз — только после повторного деплоя** (`deploy_gateway.sh`), иначе Gemini Spark продолжит видеть старый `tools/list` без аннотаций.
- **Проверка:** `python -m pytest -q` — 434 passed, 1 skipped.

### Д. Подтверждение только на установку/удаление, `sudo` и системные разделы (Локальные изменения, готовые к коммиту)
- **Что выяснилось на живой проверке:** после деплоя аннотаций `system_info`/`list_dir`/`read_file` проходят молча, а `bash_exec` продолжал спрашивать. Логи шлюза показали, что клиент **перечитал** `tools/list` уже с аннотациями (`clientInfo={'name': 'Gemini', 'version': '1.0.0'}`), то есть кэш исключён. Правило клиента совпадает с описанием в блоге MCP: `readOnlyHint: true` → «пропустить диалог подтверждения», `destructiveHint: true` → «предупреждение перед выполнением». Значит Gemini спрашивает про **любой** инструмент, который не помечен read-only, а аргументы команды клиент не читает.
- **Решение (выбрано оператором):** подсказка на один инструмент не отличает `ls` от `apt install`, поэтому политика перенесена на шлюз, и подтверждаются ровно четыре класса:
  1. **Установка/удаление ПО и удаление данных** — пакетные менеджеры, деинсталляторы, `msiexec`, `dpkg`/`rpm`, `rm`/`Remove-Item`/`del`/`rd`, `dd`/`mkfs`/`git clean -fd`/`docker prune`/`truncate -s 0`, а также `curl … | bash` и `iwr … | iex`.
  2. **`sudo`** — `sudo`, `doas`, `pkexec`, `runas`, `Start-Process -Verb RunAs`.
  3. **Системные разделы** — `/etc`, `/usr`, `/boot`, `/var/lib`, `/opt`, `/dev`, `C:\Windows`, `C:\Program Files`, `ProgramData`, реестр (`SYSTEM_PATH_RE`). **Чтение** этих путей (`cat /etc/os-release`, `systemctl status nginx`) не блокируется — блокируется только изменение (мутация или перенаправление вывода).
  4. Всё остальное — включая `write_file`, `edit_file`, `job_kill`, `share_file`, `serve_dir` — идёт **без диалога**, как и просил оператор.
- **Как это сделано:**
  1. `bash_exec` и `run_job` объявлены шлюзом read-only; шлюз разбирает команду (`classify_command()`) и на закрытый класс возвращает модели отказ с указанием переоформить вызов как `system_change` (объявлен `destructiveHint=true`, поэтому клиент спрашивает). Более специфичная причина побеждает: `sudo apt install x` сообщается как установка, а не как sudo.
  2. `write_file` и `edit_file` объявлены read-only, но системный путь в `path` отклоняется с указанием на новый `system_write` — «подтверждаемый» двойник записи, который принимает точное содержимое (никакого экранирования для оболочки).
  3. **Узел не менялся вообще:** `system_change` транслируется в `bash_exec`/`run_job`, `system_write` — в `write_file` до отправки в туннель, поэтому политика работает с любой версией узла (в том числе с установленным payload 0.2.6) и не требует обновления кода на машинах.
- **Границы:** это UX-барьер, а не песочница — обфускация команды или вызов через промежуточный скрипт его обойдут; жёсткая гарантия остаётся за `MESH_READ_ONLY`/`MESH_WRITE_ROOTS`. Поверхность узла (`core/mcp_tools.py`) остаётся честной: там нет классификатора, поэтому read-only подсказки выставляются только на стороне шлюза, а тест фиксирует список таких исключений.
- **Тесты:** `tests/test_gateway_command_policy.py` (классификатор install/delete/sudo/system, распознавание системных путей, отсутствие пересылки закрытой команды на узел, трансляция `system_change`/`system_write`, объявления), обновлён `test_advertised_confirmation_hints_match_the_node` (задокументированные исключения вместо полного паритета).
- **Проверка:** см. вывод прогона набора в коммите.

## 2. Анализ вопроса: «Есть ли смысл использовать так много инструментов для MCP из агентской среды?»

### Вердикт:
**Да, текущее разделение на 19 инструментов полностью оправдано и необходимо.** Вот почему агент не может обойтись одним лишь универсальным `bash_exec`:

1. **Ограничение контекста и лимиты Gemini:**
   - Если агент будет делать `bash_exec("cat big_file.txt")`, весь файл разом вывалится в контекст, забьёт токенный лимит модели или обрежется.
   - Специализированный `read_file(path, start_line, end_line)` позволяет агенту читать файлы постранично и точно исследовать код.
2. **Безопасность редактирования:**
   - Редактировать файлы через bash (sed, awk, echo) из LLM чревато синтаксическими ошибками, проблемами с экранированием кавычек и спецсимволов.
   - `edit_file(path, old_string, new_string)` и `write_file` гарантируют атомарность и точечную правку без потери содержимого.
3. **Проблема жесткого таймаута Gemini (25-30 секунд):**
   - У клиентов Gemini (особенно в Web/App Spark) есть строгий тайм-лимит на один ответ инструмента (около 30 с).
   - Команды вроде `npm install`, `docker build`, `git clone` или бэкапы гарантированно упадут по таймауту в обычном bash.
   - Связка `run_job` + `job_output` / `job_list` / `job_kill` — единственный способ для мобильного агента запускать тяжёлые фоновые процессы и возвращаться за результатом.
4. **Кроссплатформенность (Windows):**
   - На Windows без Bash вызовы `grep`, `find`, `ls -la`, `ps aux` не работают или требуют громоздких конструкций PowerShell.
   - Инструменты `grep_search`, `glob_find`, `list_dir`, `system_vitals` работают на чистом Python одинаково на любой ОС.

## 5. Поддержка Android/Termux (смартфоны и планшеты)

**Дата:** 2026-10-08  
**Что сделано:** тот же `install.sh` ставит узел на телефон без root; `core/domain.py` и `core/agent.py` учитывают особенности Android.

### Почему нельзя было просто «запустить install.sh как на Linux»

| Особенность Android/Termux | Что ломалось | Как исправлено |
| :--- | :--- | :--- |
| Нет `/etc`, `/bin`, `/usr` (не FHS), нет root | Подсказка `sudo tee /etc/antigravity-mesh/domain.env` невыполнима; узел искал домен не там | Termux определяется отдельно; файл домена — `~/.config/antigravity-mesh/domain.env` и в установщике, и в `core/domain.py` |
| Нет `sudo`, пакеты называются иначе (`python`, `python-pip`, `python3` — виртуальное имя) | Ветка `apt-get install python3-pip python3-venv` падала, `run_privileged` не срабатывал | Ветка `pkg install -y python python-pip python-ensurepip-wheels curl ca-certificates`, установщик `pkg` идёт напрямую, без `sudo` |
| `uv` публикует сборки под glibc | Скачивание `aarch64-unknown-linux-gnu` на bionic → «Exec format error» | На Termux `UV_TARGET` пуст, uv не используется; при неудаче установщик падает закрыто с подсказкой `pkg` |
| Нет systemd и launchd | Юнит/plist не создавались, автозапуска не было | Служба **runit** (`termux-services`) + скрипт **Termux:Boot**; без `termux-services` — запуск через `nohup` с честным предупреждением |
| Android отвечает `localhost` на `gethostname(2)` у всех устройств | Все телефоны заявляли одно имя и бесконечно выбивали друг друга с шлюза | Имя узла — модель устройства (`getprop ro.product.model` → `pixel7pro`) в `install.sh` и в `default_node_name()` |
| Нет `hostname`, `systemctl status` | Пустое имя хоста, непонятные подсказки при сбое | Имя берётся через `getprop`, диагностика печатает `sv status` и путь к логу runit |
| Буфер обмена — Android | Ссылку MCP нельзя было вставить в приложение Gemini | `termux-clipboard-set` (Termux:API) первым в цепочке копирования |
| Шлюз в приватной сети (запись в `hosts`, Tailscale, VPN) | Телефон в мобильной сети получал `curl: (6) Could not resolve host`; установщик молча ничего не скачивал и падал позже с «Failed to obtain authentication token» | `require_gateway_dns()`: проверка до bootstrap и до регистрации. При коде возврата curl 6 установка останавливается **до** любых записей и объясняет причину; плюс проверка, что bootstrap действительно скачал `core/agent.py` |

### Диагностика, найденная при живой проверке (2026-10-08)

`smart-server.online` резолвится **только на машине владельца** — записью
`192.129.148.93 smart-server.online` в `C:\Windows\System32\drivers\etc\hosts`:

* публичные резолверы (8.8.8.8, 1.1.1.1, 9.9.9.9) отвечают NXDOMAIN — записи в DNS нет;
* Tailscale это имя не маршрутизирует: в `tailscale dns status` split-DNS есть только для `ts.net.`;
* поэтому на телефоне имя не резолвится ни в мобильной сети, ни в Wi-Fi, ни с включённым Tailscale.

## 6. Ветка устройства: `device_info` / `device_control` / `device_capture` / `device_messages`

**Дата:** 2026-10-09  
**Что сделано:** поверхность инструментов выросла с 20 до **24**: четыре инструмента работают с самим устройством, на котором запущен узел, — телефоном под Termux или собственным ноутбуком/сервером. Всё подчинено одному правилу: `tools/list` объявляется шлюзом для **каждого** узла статически, поэтому «телефонный» инструмент не может исчезнуть на ноутбуке — различается **ответ**: `available: false`, причина и, где она есть, подсказка `fix`.

### Новые модули

1. **`core/device.py`** — телеметрия устройства на всех платформах: Android/Termux (`termux-api`, `/proc`, `/sys`, `getprop`), Linux (`/sys/class/power_supply`, `iw`/`nmcli`), Windows (`ctypes`, `winreg`, CIM там, где иначе не выйдет), macOS (`pmset`, `sysctl`, `airport`, `system_profiler`). Разделы: `device`, `battery`, `network`, `locale`, `time`, `hardware`, `storage`, `cameras`, `microphones`, `sensors`, `capabilities`.
   - **Для чего:** один контракт вместо четырёх наборов проб. Коллектор не бросает исключений: блок без ответа отдаёт `available: false` + `reason`, у каждого блока есть `source`, всё собирается в одном пуле под общим дедлайном (замороженное приложение Termux:API или `system_profiler` не задерживают `system_info`), результат кэшируется на несколько секунд и обходится через `fresh=true`. Модель не должна читать «0 %» там, где правда — «платформа этого не отдаёт».
2. **`core/termux.py`** — единственное место в узле, откуда запускаются команды `termux-*`.
   - **Для чего:** Termux:API — установка из двух частей (пакет даёт команды, приложение отвечает на них по binder), и отсутствие любой из половин выглядит одинаково — молчанием. Поэтому вызов идёт только argv-списком, без оболочки, под жёстким таймаутом, а отказ возвращается словарём: `missing` (нет команды), `denied` (Android не дал разрешение, и известно какое), `timeout` (приложение заморожено), `refused` (не `termux-*`). Здесь же реестр возможностей, карта «команда → разрешение», наблюдённые состояния разрешений и ref-counted wake lock.

### Инструменты

1. `device_info` — **только чтение, подтверждение не запрашивается**: отчёт об устройстве одним вызовом (батарея и зарядка, сетевые интерфейсы с Wi-Fi и сотовым сигналом, язык, время и часовой пояс, CPU, ОЗУ, накопитель, камеры, микрофоны, датчики, возможности). `section=summary|all|device|battery|network|locale|time|hardware|storage|cameras|microphones|sensors|capabilities`, плюс `sensor` (один живой замер с датчика по имени), `fresh` и `quick`.
2. `device_control` — **обычная локальная работа, подтверждение не запрашивается**: 20 обратимых действий — `torch`, `vibrate`, `volume`, `volume_get`, `brightness`, `tts_speak`, `toast`, `notify`, `notify_list`, `notify_remove`, `clipboard_get`, `clipboard_set`, `media`, `media_scan`, `wakelock`, `download`, `open`, `share`, `dialog`, `wallpaper`. Каждое действие — фиксированная команда `termux-*`; текст из аргументов модели уходит одним элементом argv и никогда не разбирается оболочкой.
3. `device_capture` — **всегда спрашивает подтверждение**: 11 действий — `camera_list`, `camera_photo`, `mic_record_start`, `mic_record_stop`, `mic_record_status`, `location`, `fingerprint`, `usb_list`, `usb_access`, `infrared_frequencies`, `infrared_transmit`. Фото и запись ложатся в каталог съёмки узла и сами никуда не отправляются; `fingerprint` возвращает только вердикт, биометрия на узел и шлюз не попадает; `usb_access` запрашивает у Android разрешение и отдаёт дескриптор, но `termux-usb -e <program>` намеренно не выставляется — имя программы из аргумента модели никогда не доходит до exec.
4. `device_messages` — **всегда спрашивает и выключен, пока оператор не включит**: 5 действий — `sms_list`, `sms_send`, `call_log`, `contacts`, `call`. Пока `MESH_DEVICE_PIM` не равен 1, отказ называет флаг и разрешения Android, которые нужно выдать, то есть ответ является инструкцией, а не тупиком: это личные данные того, у кого телефон в руках.

### `system_info`, `system_vitals`, `mesh_status`, `run_job`

1. `system_info` теперь несёт все блоки устройства (батарея и зарядка, сеть и сигнал, язык, время и часовой пояс, CPU, ОЗУ, накопитель, камеры, микрофоны, датчики) — ровно то, что просил пользователь. Блоки собираются под `DEVICE_DEADLINE` (7 с) в одном пуле, поэтому медленный источник не задерживает status-вызов, а неответивший блок говорит причину вместо нуля.
2. `system_vitals` дополнен блоком батареи и термическими датчиками (тот же кэш, что у `system_info`, — второй вызов ничего не стоит). Для ноутбука батарея и есть главный «vital», для телефона к ней добавляется температура.
3. `mesh_status` теперь сообщает `device_class`, `scenario` и `battery_percent` (плюс `device_model` и `on_battery`, когда они есть): модель обязана знать, что разговаривает с телефоном на батарее, до того как запустит сборку.
4. `run_job` на Android автоматически берёт wake lock на всё время задачи и отпускает его при завершении или `job_kill`. `wake_lock` есть в результате `run_job` и в записи `job_list` (текущее состояние: `true`, пока задача идёт, и `false` после освобождения), а телефон, отказавший в блокировке, получает `wake_lock_note` с подсказкой.
   - **Для чего:** Android замораживает фоновое приложение при выключенном экране, и здоровая сборка превращается в задачу, которая никогда не заканчивается. Аргументом это сделано намеренно: модель, которая забыла бы его передать, получила бы задачу, молча останавливающуюся при гашении экрана.
   - **Освобождение ровно один раз на задачу:** `job_kill` и поток-жнец финализируют одну и ту же задачу, а блокировка ref-counted по задачам, поэтому двойное освобождение снимало бы защиту с *другой*, всё ещё работающей задачи. Освобождение «заявляется» один раз (`_WAKE_LOCK_RELEASED`), и это проверено тестом `test_killing_one_job_does_not_release_another_jobs_wake_lock`.

### Переключатели оператора

| Переменная | По умолчанию | Что делает |
| :--- | :--- | :--- |
| `MESH_DEVICE` | `auto` | `auto` — ветка отвечает на всех платформах (меняется только ответ), `0` — выключает ветку, `1` — включает принудительно. |
| `MESH_DEVICE_ACTIONS` | пусто | Allowlist имён действий через запятую для трёх action-инструментов; пусто — все действия сборки. |
| `MESH_DEVICE_CAPTURE_DIR` | общее хранилище телефона после `termux-setup-storage`, иначе `~/.cache/antigravity-mesh/captures` | Куда пишутся фото и записи. |
| `MESH_DEVICE_PIM` | `0` | `1` включает SMS, журнал вызовов, контакты и звонок. |
| `MESH_DEVICE_QUICK` | `0` | `1` оставляет `system_info` мгновенным, пропуская сеть, камеры, микрофоны и датчики. |
| `MESH_READ_ONLY` | `0` (существующий флаг) | Теперь дополнительно отказывает в каждом действии `device_control`/`device_capture` и блокирует `sms_send` и `call`. |

Все они читаются в `core/agent.py::configure_from_env` и применяются в `core/mcp_tools.py::configure`; `MESH_DEVICE_CAPTURE_DIR` дополнительно читается самим `core/device.py::capture_dir`, а `MESH_DEVICE=auto` оставляет ветку объявленной везде именно потому, что статический `tools/list` шлюза должен совпадать с поверхностью узла.

### Политика подтверждений: почему `device_capture` и `device_messages` «деструктивные»

1. **Что сделано:** для них заведён профиль `_ANNOTATIONS_SENSITIVE`, совпадающий по значениям с деструктивным (`destructiveHint: true`), хотя эти инструменты ничего не удаляют. `device_info` отнесён к read-only, `device_control` — к обычной локальной работе.
2. **Для чего:** `destructiveHint` — единственная подсказка, которую клиенты вроде Gemini Spark надёжно превращают в вопрос «подтвердить действие?», а камера, микрофон или список SMS не должны срабатывать молча. Пометить так же фонарик или вибрацию — значит приучить пользователя закрывать те диалоги, которые действительно важны.
3. **Компромисс зафиксирован в README** (обе языковые половины) и в `docs/TERMUX.md`: классификация честная в смысле безопасности, но не буквальная — инструменты удаления здесь ни при чём, и это сказано прямо.
4. **Тест `tests/test_tool_annotations.py`** пинует обе границы в обе стороны: набор деструктивных инструментов равен `{mesh_update, unshare, device_capture, device_messages}`, а `device_control` обязан остаться без `destructiveHint`.

### Проверка на реальном устройстве (OPPO PHY110, Android 16, Termux)

Ветка проверялась не только тестами: узел `localhost-602` — настоящий телефон, и через живой шлюз сняты реальные ответы (`tools/probe-node.py`, фикстуры в `tests/fixtures/termux/`). Что это дало:

1. **Найден и исправлен баг установщика.** `ensure_termux_extras` считал пакет `termux-api` установленным по наличию `termux-wake-lock`. На этом телефоне `termux-wake-lock` был, а `termux-battery-status`, `termux-sensor`, `termux-camera-info` и все остальные команды отсутствовали, поэтому установщик молчал, а ветка устройства осталась бы мёртвой без единого объяснения. Теперь проверяется команда, которую даёт только сам пакет (`termux-battery-status`), а в финальной подсказке установщика появились пункты про разрешения Termux:API и переключатели `MESH_DEVICE*`.
2. **Пакет установлен на телефон** (`pkg install -y termux-api`, версия 0.60.0) — с согласия владельца устройства.
3. **Воспроизведён отказ «приложение Termux:API не установлено»:** все команды теперь существуют, но каждая виснет (`timeout 8` → код 124), потому что отвечает на них отдельное приложение Termux:API, а его на телефоне нет. Это тот самый случай, под который писались жёсткие таймауты; в `core/termux.py` добавлено запоминание такого зависания (`capabilities()["app_reachable"]` = `true`/`false`/`null` + `app_fix`), а `device_info`/`system_info` при нескольких зависших разделах называют одну общую причину (`hint`/`device_hint`) вместо пяти одинаковых «timed out».
4. **Файловые источники проверены на настоящих данных:** `getprop` (модель `PHY110`, производитель `OPPO`, Android 16, `ru-RU`, `Asia/Tbilisi`, `characteristics=nosdcard`), `/proc/meminfo` (15 568 920 кБ), термальные зоны в миллиградусах, частоты CPU (787 200 / 2 265 600 кГц), отсутствие `~/storage/shared`. Эти значения стали фикстурами и проверяются тестами, а не остаются предположениями. Термальные зоны реального телефона заодно показали мусор, который раньше попадал в отчёт: `mmw0 = -273000` (незаполненный датчик) и `pm8550-bcl-lvl0 = 0` (это уровень тока, а не температура). Теперь физически невозможные значения отбрасываются, а зоны вида `*-lvl*`/`*-bcl*` не выдаются за градусы.
5. **Тесты нашли ещё три вещи, которые исправлены:** батарея macOS сообщала `charging` для разряжающегося Mac (слово `discharging` содержит `charging`); блок `network` считал сеть найденной, когда соты вернули только причину отказа (`available: true, interface_count: 0`); однострочный `signal` описывал LTE, пока трафик шёл через Wi-Fi, и противоречил полю `connected_kind`. Теперь сводка называет тот канал, который реально несёт трафик, а второй радиоинтерфейс остаётся в блоках `wifi`/`cellular`.
6. **Приложение Termux:API установлено на телефон — и настоящие ответы вскрыли две ошибки в парсерах.** F-Droid-сборка на этом телефоне **не ставится**: аддоны Termux делят `sharedUserId` с Termux и обязаны быть подписаны тем же ключом, а Termux здесь поставлен APK-файлом с GitHub (`installer=com.android.packageinstaller`, `TERMUX_VERSION=0.118.3`). GitHub-сборка `termux-api-app_v0.53.0+github.debug.apk` установилась сразу (sha256 сверен с опубликованным), после запуска приложения команды начали отвечать. В реальных ответах нашлось то, чего нет в документации:
   - Wi-Fi отдаёт частоту как **`frequency_mhz`**, а парсер читал `frequency` — частота молча терялась;
   - отказ в разрешении приходит **успешным вызовом**: `{"error": "Please grant the following permission to use this command: android.permission.ACCESS_COARSE_LOCATION"}` на stdout с кодом 0. Адаптер смотрел только код возврата, поэтому «Android не дал разрешение» превращалось в пустой ответ; теперь это `ok: false` + `denied` + `fix` с именем разрешения, и оно запоминается в `capabilities().permissions`.
   Оба случая закрыты регрессионными тестами на **реальных** фикстурах (`tests/test_phone_payloads.py`), сами ответы лежат в `tests/fixtures/termux/` вместе с `README.md` о происхождении данных. Съём — `tools/probe-node.py` (или `tools/capture-termux-fixtures.sh` на самом телефоне). Отдельно выяснено правило политики узла: он блокирует **любое перенаправление вывода** (`2>/dev/null`) как «запись в системный путь», поэтому пробник больше не использует редиректы.

### Что осталось

1. **Выдать Termux:API разрешения тапом на телефоне** (`Настройки → Приложения → Termux:API → Разрешения`): местоположение, телефон, камера, микрофон, уведомления, SMS, журнал вызовов, контакты, файлы/фото. — **сделано**: все нужные разрешения выданы (`ACCESS_FINE_LOCATION`, `READ_PHONE_STATE`, `CAMERA`, `RECORD_AUDIO`, `READ_SMS`, `READ_CONTACTS`, `POST_NOTIFICATIONS` — `granted=true`), после чего пересняты **настоящие** ответы: Wi-Fi с реальным SSID и RSSI −65 dBm, соты (зарегистрированная ячейка `dbm −102, level 2, type lte`, оператор `Cellfie`), 4 камеры, 46 датчиков, громкость, TTS, USB, ИК. Через `adb` разрешения выдать не удалось: ColorOS запрещает `pm grant`/`appops set` из shell.
   - Форма отказа сохранена отдельной фикстурой `tests/fixtures/termux/permission-denied.json` (это настоящий ответ телефона до выдачи разрешения): без неё регрессия «отказ = пустой ответ» вернулась бы незаметно, потому что `telephony-cellinfo.json` теперь содержит реальные соты.
2. Убедиться, что `device_info(section="all")` на телефоне заполняет все блоки, а не отвечает `available: false` (для этого ветку нужно сначала выкатить на телефон: узел `localhost-602` пока работает на релизной сборке).
3. **Найдена дыра в живучести телефона:** Android выгрузил приложение Termux целиком (в `ps -A` не осталось ни одного процесса), и узел не поднялся сам — ни службы runit, ни `~/.termux/boot`, ни лаунчера в `~/.config/antigravity-mesh/` на этом телефоне нет (пакет `termux-services` не установлен, Termux:Boot не настроен). Узел вернулся только после того, как Termux открыли заново (login-shell поднимает супервизор), а затем апдейтер применил обновление и перезапустил агента. Строка об этом добавлена в `docs/TERMUX.md` (обе половины); на таком телефоне стоит выполнить `pkg install termux-services` и настроить Termux:Boot.
3. После выката — повторный деплой **развёрнутого** шлюза (`deploy_gateway.sh`): в исходниках `gateway.py` четыре инструмента и их аннотации уже есть, но клиенты Gemini Spark увидят их только после того, как обновится работающий шлюз (та же оговорка, что и в разделе Г).
   - **Найдено при живой проверке:** развёрнутый шлюз печатает `system_info` своим белым списком полей, и блоки устройства в этот список не входили — то есть телеметрия терялась бы даже после передеплоя. Форматтер в `gateway.py` расширен (`_device_report_lines`): батарея, сигнал, локаль/время, ЦП/ОЗУ/термальные зоны, накопитель, камеры/микрофоны/датчики, `capabilities` и подсказка `device_hint`; недоступный блок печатается как `available: false` с причиной и `fix`, а не как ноль. Закрыто двумя тестами в `tests/test_gateway_share_route.py`.
   - ⚠️ **Расхождение, которое нужно решить перед передеплоем:** работающий шлюз объявляет 22 инструмента, включая `system_change` и `system_write`, которых **нет ни в этом чекауте, ни в установленном payload 0.2.6**. Если развернуть шлюз из этого репозитория как есть, эти два инструмента исчезнут из `tools/list` у клиента. Либо деплоить из источника, где они есть (и перенести туда ветку устройства), либо сознательно принять их потерю.
4. Решить, нужен ли `termux-job-scheduler` для задач, переживающих перезагрузку телефона: сейчас `run_job` защищён только wake lock'ом на время своей жизни.
5. `_release_job_wake_lock` при недоступной мете задачи не освобождает блокировку (выбирает утечку вместо снятия чужой защиты) — сознательный компромисс, но стоит перепроверить, если появятся жалобы на «телефон не засыпает».
6. Сознательно отложено: платформенный `tools/list` (узел сообщает шлюзу набор возможностей, шлюз кэширует список на узел). Сейчас ветка объявлена на всех платформах именно потому, что статический список шлюза обязан совпадать с поверхностью узла; 24 инструмента в этот лимит укладываются, но если клиент упрётся, фаза потребует правки протокола шлюза и переписывания parity-теста на capability-aware.

## 7. Файл домена записывает сам установщик

**Дата:** 2026-10-09  
**Что сделано:** `install.sh` и `install.ps1` записывают разрешённый публичный домен в файл домена строкой ровно `MESH_PUBLIC_URL=https://<хост>` — кроме встроенного значения по умолчанию.

### Почему это было нужно

`core/domain.py` разрешает публичный домен по цепочке `MESH_PUBLIC_URL` → `AGY_PUBLIC_BASE_URL` → файл домена → встроенное значение по умолчанию, а устаревший `MESH_GATEWAY` (он лежит в `agent.env`) читает **только** `gateway_host()` — хост туннеля. Поэтому узел, поставленный обычным способом (`agent.env` с `MESH_GATEWAY`/`MESH_USER`/`MESH_TOKEN` и без файла домена), звонил на правильный шлюз, а публичные ссылки строил на встроенном домене. Случай наблюдался вживую: телефон под Termux публиковал ссылки вида `https://<встроенный-домен>/<узел>/<слаг>/`, хотя его туннель шёл на тот шлюз, где он зарегистрирован.

### Что именно сделано

1. **`install.sh`** пишет файл домена в обеих ветках установки — standalone и «облачный шлюз/туннель» сразу после `agent.env`. Путь: `/etc/antigravity-mesh/domain.env`, в Termux — `$HOME/.config/antigravity-mesh/domain.env`, в Git Bash — `%USERPROFILE%\.config\antigravity-mesh\domain.env`; переопределяется `MESH_DOMAIN_FILE`, и создаётся каталог именно того файла, который используется (раньше при несуществующем каталоге из `MESH_DOMAIN_FILE` создавался путь по умолчанию, и запись падала).
2. **`install.ps1`** делает то же на Windows — сразу после записи `agent.env` и до запуска агента.
3. **Оба нормализуют значение** (схема или завершающий слэш не могут попасть в строку дважды), **не переписывают** файл, если он уже называет тот же хост, и **никогда не пишут** плейсхолдер `__MESH_DOMAIN__` или пустое значение.
4. **Встроенное значение по умолчанию не записывается:** если разрешённый хост совпадает с `DEFAULT_PUBLIC_BASE_URL` из `core/domain.py`, запись пропускается. Это запасной вариант, а не конфигурация: закреплённый файл домена превратил бы «ничего не настроено» в конфигурацию, а при наличии такого файла `core/domain.py` вовсе перестаёт обращаться к устаревшему `MESH_GATEWAY` — позднейшая правка `agent.env` оператором молча игнорировалась бы. Потерь нет: без файла то же значение и есть последняя ступень резолвера, поэтому ссылки узла и его туннель по-прежнему называют один хост.
5. **Ветка `--ssh=` передаёт домен цели:** `install.sh` добавляет удалённому установщику `--domain=<домен>`, разрешённый на этой машине, поэтому удалённый хост записывает тот же домен, а не разрешает его заново (копия из репозитория с плейсхолдером в `$PUBLISHED_DOMAIN` иначе ушла бы на встроенное значение).
6. **Запись не фатальна:** если файл записать нельзя (нет `sudo` для `/etc`, закрытый профиль), установка продолжается, а установщик печатает точную команду для ручного запуска.
7. **Сухие прогоны** (`install.sh --dry-run`, `install.ps1 -DryRun`) сообщают файл и значение, которое было бы записано, — включая явный пропуск `not written (the built-in default is a fallback, not a configuration)`, — и по-прежнему ничего не меняют на диске.
8. **На стороне шлюза** поведение не менялось: `deploy_gateway.sh` и раньше писал `/etc/antigravity-mesh/domain.env` на хосте шлюза.

**Оговорка про `MESH_DOMAIN_FILE`.** Это переопределение только **пути**, и оно принадлежит конфигурации узла, а не запуску установщика: узел читает переменную из своего окружения (ключи `MESH_*` из `agent.env` экспортируются при старте `core/agent.py`), поэтому значение, выставленное лишь на время установки, отправит домен в файл, которого узел никогда не прочитает.

### Уже установленный узел

Достаточно повторного запуска установщика или одной строки вручную: `mkdir -p ~/.config/antigravity-mesh && echo 'MESH_PUBLIC_URL=https://<домен>' > ~/.config/antigravity-mesh/domain.env` (Termux/Windows) либо то же через `sudo tee /etc/antigravity-mesh/domain.env` в Linux. Уже выданные ссылки продолжают работать, новые берут настроенный домен. Если настроенный домен и есть встроенное значение по умолчанию, файла не будет — так и задумано.

### Файлы

- `install.sh`, `install.ps1` — запись нормализованного домена в файл домена (обе ветки; на Windows — после `agent.env`), пропуск встроенного значения по умолчанию, создание каталога используемого файла, передача домена по `--ssh=`, отчёт в сухом прогоне, нефатальная запись с подсказкой для ручного запуска.
- `README.md`, `docs/TERMUX.md`, `docs/GUI_INSTALLER.md`, `docs/DOMAIN.md` — где лежит файл домена, что и когда его пишет установщик, почему встроенное значение не записывается, что `MESH_DOMAIN_FILE` — настройка узла, а не установщика, и как поправить уже установленный узел.
